# AI Agent 时代如何打造高质量软件

> 质量是系统工程，测试不是唯一环节。在 Vibe Coding 加速开发的同时，质量保障必须从验证确定性代码，升级为管理系统行为的不确定性。

## AI 生成代码带来的质量悖论

AI 编程工具显著提高了原型、功能和重构的速度，但“代码生成得更快”不等于“软件质量自然提高”。

AI 生成的代码常见以下风险：

- 局部实现看起来完整，但未必符合系统整体架构。
- 能快速覆盖常规路径，却可能遗漏边界条件和异常恢复。
- 会根据上下文作出合理猜测，但这些假设未必写在需求中。
- 开发速度超过人工评审和传统测试用例编写的速度。

这会形成一种新的技术债：代码在提交时看起来可以工作，但未经验证的架构假设、业务规则和异常行为隐藏在实现中，直到集成、预发或生产阶段才暴露。

质量保障不能只问“代码能不能运行”，还需要回答：

- 实现是否忠实于需求？
- 需求本身是否存在歧义或矛盾？
- AI 是否遗漏了边界和异常场景？
- 系统在依赖失败、超时和数据异常时能否恢复？
- 测试结论是否有可复现的证据？

## 从验证正确性到管理不确定性

传统软件通常强调确定性：给定输入，程序应产生可预测的输出。AI Agent 则可能根据上下文选择不同工具、构造不同参数，并形成不同的推理和执行路径。

即使最终输出看起来合理，中间过程仍可能存在问题：

- 选择了错误的工具。
- 使用了正确工具但传入错误参数。
- 检索到了不相关或过时的信息。
- 在上下文截断后忽略关键约束。
- 多个 Agent 之间传递了不完整状态。
- 外部依赖失败后仍给出无依据的结论。

测试对象因此从最终输出扩展为完整行为链路。质量团队需要验证工具选择、参数构造、状态传递、失败恢复、数据来源和最终结果。

## Agent-CI：把质量门禁放进开发过程

面向 AI 开发的质量体系需要覆盖设计、开发和部署前阶段。

### 设计阶段：让 AI 检查需求

在编码开始前，可以使用 LLM 检查 PRD、Prompt 和接口约定中的模糊表达、冲突规则、缺失的异常处理、无法量化的验收条件，以及安全和隐私边界。

AI 不应替代产品决策，但可以把隐含问题转换为需要人回答的明确问题。

### 开发阶段：隔离并验证生成代码

AI 生成的代码应在受控环境中完成构建、测试和依赖访问。使用 RAG 或外部工具的 Agent 还需要隔离测试知识库、账号和第三方服务，避免污染生产数据。

静态检查、单元测试、接口测试和安全检查应成为合并代码的证据，不能把“AI 认为实现正确”当作证据。

### 部署前：验证故障和恢复行为

预发环境需要主动模拟现实故障，例如：

- API 超时、限流或不可用
- Token 或上下文被截断
- 检索结果为空、冲突或过期
- 工具返回格式发生变化
- 模型拒绝回答或输出无效结构

目标不是证明系统永不失败，而是确认系统能够识别失败、限制影响、保留证据并安全恢复。

## 测试人员的角色变化

AI Agent 时代的测试人员不再只是编写脚本和报告缺陷，更重要的职责包括：

- 设计质量策略和风险模型。
- 指导 AI 生成有价值的测试，而不是堆积重复用例。
- 审核 AI 对需求和故障的判断。
- 建立可衡量的质量门禁。
- 管理测试知识、历史缺陷和领域规则。
- 确定哪些关键决策必须由人审批。

AI 可以阅读大量文档、提出候选场景、生成数据和分析日志；人负责定义目标、判断风险、审阅结论并处理伦理、安全和合规问题。

## 用证据驱动开发管理 AI 技术债

修改 Prompt、模型或 Agent 工作流之后，“感觉效果更好”不是可靠的验收方式。改动需要由可比较的数据支持，例如需求覆盖、已识别风险、测试结果、工具调用正确性、响应时间、人工复核和线上可观测性反馈。

测试报告不应只展示通过或失败，还应保留输入、执行路径、关键输出和诊断依据，以便复现和审计。

## 人类必须在环

AI 可以扩大测试覆盖面，但不应获得无限制的决策权。医疗、法律、金融、安全、权限、隐私、生产数据修改和发布决策尤其需要人工审核。

人类在环不是降低自动化程度，而是把人工注意力集中在高风险和高价值节点。

## AI 测试产品应该具备什么

面向 Vibe Coding 的 AI 测试工具可以从需求和接口文档开始：

1. 读取 PRD、Markdown 或 OpenAPI 文档。
2. 使用 LLM 识别歧义、矛盾、缺失要求和可测试性风险。
3. 生成功能、边界、异常和 API 测试用例。
4. 把结构化用例交给人审阅，而不是直接盲目执行。
5. 确定性执行接口测试或 pytest。
6. 使用 LLM 分析失败原因，同时保留原始证据。
7. 输出适合开发者和 CI 使用的报告。

后续还可以构建场景策略、历史缺陷 RAG、性能测试、故障注入、Playwright UI 自动化、用例版本管理、团队协作，以及能够调用生成、执行、分析和报告工具的测试 Agent。

## LingTest CLI 的实现方向

LingTest CLI 将确定性测试引擎和 AI 能力放在同一条可审阅工作流中：

```text
PRD / OpenAPI
    → AI 需求分析
    → AI 生成结构化测试计划
    → 人工审阅
    → 确定性执行
    → AI 失败诊断
    → JSON / JUnit 证据
```

确定性能力不依赖模型，保证基础测试可以重复执行；AI 能力通过独立 Provider 接入，用于理解文档、扩展测试思路和辅助诊断。所有 LLM 输出必须经过结构化校验，不能把任意文本直接当作可执行测试。

## 结语：从守门员到质量架构师

AI 提高了软件生成速度，也扩大了系统行为的不确定性。未来的质量团队会更早参与需求、更重视证据和可观测性，并把 AI 当作测试协作者。

不是没有人做测试，而是测试不再只依赖人亲自完成。人的价值从执行测试，转向定义可信软件应满足的条件。
